# 玩法增量制作

## 适用范围

实现当前任务要求的玩法。局部 HUD 或冷却修改保持局部范围；完整游戏先做可操作的代表性场景，再增加内容数量。

## 输入事实

读取当前技术方案、卡片目标、工作区、相关文件及已有检查结果。确认对象/组件或 ECS 的实际更新入口和状态所有者，保留 Miniplex 查询与现有组件边界。

## 工作方法

先追踪输入意图 → 模拟状态 → 表现 → UI，确定修改归属。沿用已有架构、物理实现和包管理器，不因示例偏好替换框架。
增量实现并保留原功能；UI 从实际状态读取，不维护另一套冷却或胜负规则。完整玩法按用户意图确定交互与反馈；休闲探索、叙事、无失败设计不强加战斗压力、奖励或失败惩罚。
时间行为涉及冲刺、冷却、暂停、重开时，装配器提供 [时间与状态](references/time-and-state.md)；普通改色等任务不需要该资料。未提供时不得声称读过，也不调用不存在的 skill.read。
复用当前任务记录交接完成工作和待处理项，不创建重复策划文件。先让一个代表性场景达到目标，再扩大关卡或素材数量。凭据存在不代表外部生成与付费已获授权。

## 常见失败

输入无法触发逻辑；状态变化未到 UI；新增组件不在查询里；重开后事件重复订阅；通过删功能、关闭检查或替换工程制造成功。编辑冲突应重读当前文件和准确前文。

## 完成依据

说明旧行为保留情况、实际写入和当前检查结果。仅在提供的工具与有效授权内检查或构建；失败依据具体诊断修复根因。构建通过不等于实际操作通过，没有浏览器观察与真实输入证据就明确尚未验证。
